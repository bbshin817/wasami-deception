# 実装進捗記録の運用ルール

`.claude/progress/` は「進行中の作業がどこまで進んだか」の記録。セッションの中断（クラッシュ、`/clear`、コンテキスト圧縮、別セッションへの引き継ぎ）がどのタイミングで起きても、**記録と git とエディタのアセットの状態だけから安全に再開できる**ことを目的とする。WebGL 版の同名のルールを UE5 版に合わせたもの。

## 構成

| パス | 内容 |
| --- | --- |
| `progress/<YYYYMMDD>-<slug>.md` | 進行中の作業 1 件につき 1 ファイル |
| `progress/_template.md` | 新規記録のひな形 |

`_template.md` 以外のファイルがあれば、それは未完了の作業。

## 対象

- ファイルやアセットの変更を伴う作業は、規模にかかわらずすべて記録を作る。
- 1 コミットで終わる小さな作業は、frontmatter と「依頼」「計画」「次にやること」だけ書けばよい。
- 質問への回答や調査だけで、何も変えない作業は対象外。

## 更新のタイミング（先に書いてから作業する）

1. **作業開始時**: 変更する前に記録を作る。依頼の要旨、ブランチ、開始時の HEAD（`base`）、ステップに分けた計画を書く。
2. **各ステップの開始前**: そのステップを「作業中」にし、変更する予定のファイルとアセット（`/Game/...` のフォルダ）を書く。
3. **各ステップのコミット直前**: そのステップを完了にし、「次にやること」を更新して、記録もステージしてからコミットする。
4. **判断したとき、ユーザーの回答を得たとき**: その場で「決定事項」に理由と一緒に書く。人に聞けずに仮で決めたこと（無人モード。`.claude/guides/autonomy.md`）は「要確認（ユーザー）」に書き、答えが出たら「決定事項」に移す。
5. **時間のかかる処理や、途中で止まると中間状態が残る処理の前**（アセットの一括取り込み、レベルの組み立て、C++ のビルドとエディタの開き直し、シェーダーのコンパイル待ちなど）: 実行する手順、出力先、完了の確かめ方を「再開時の注意」に書く。
6. **計画が変わったとき**: 計画を書き換え、変更の理由を「決定事項」に書く。
7. **作業完了時**: 最後のコミットで記録ファイルを削除する（経緯は git 履歴に残る）。

## 書き方

- 記録だけを読めば続きができるように書く。会話の文脈に頼る書き方（「さっきの案」「上記のとおり」）はしない。
- ユーザーが示した条件や制約は、原文に近い形で「依頼」に残す。
- ステップは 1 コミットで終わる大きさに分ける。
- エディタの状態（開いているレベル、保存していないアセット、PIE、動かしたままのプロセス）は「再開時の注意」に書く。

## 実装が終わったら `/clear` を求める

2026-09-16 のユーザーの指示（「コンテキストの肥大化による精度低下を防ぐため、実装が完了したら進捗・内容を `.claude/` 配下へ保存し、ユーザへ `/clear` の実行を求める。大規模な実装はステップにわけ、ステップごとに進捗と再開可能な記録を残し、同様の要求を行う」）。

- **実装が 1 つ終わったら、そこまでを `.claude/` の下に残してから、ユーザーに `/clear` をお願いする。** 会話が長いほど精度が落ちるので、続きは新しいセッションで始める。
- 残すもの（`/clear` の前に必ず）:
  - 実装記録（`.claude/implementation-records/`）を現行実装に合わせ、`python .claude/scripts/check_records.py` を OK にする。
  - 次の一歩が変わったなら `.claude/references/handover.md` の「現状と次の一歩」を直す。
  - まだ終わっていない作業があるなら進捗記録（`.claude/progress/`）を残す。終わったなら消す。
  - コミットする（push の条件を満たしていれば push も）。
- お願いするときは、**何が終わったか・次に何をするか・再開のために読むファイル**を 1〜3 行添える。
- **大規模な実装はステップに分ける。** 1 ステップは「記録だけを読めば次のセッションが続きを始められる」大きさにし、ステップごとにコミットと記録の更新をして、同じように `/clear` をお願いする。
- `/clear` の後は、下の「再開の手順」から始める。
- **無人モード**（`.claude/guides/autonomy.md`）では `/clear` を頼まず、状態ファイル `Intermediate/Overnight/status.json` を書いて応答を終える。駆動役 `Tools/overnight.py` が新しいセッションで `/continue` を始める。

## 再開の手順

セッション開始時、`/clear` の後、コンテキスト圧縮の後、「続きから」と言われたときは、ほかの作業より先に次を行う。
**この手順は `/continue` スキル（`.claude/skills/continue/SKILL.md`）が具体的なコマンドつきで実行する形にしてある。**
セッション開始の hook（`.claude/scripts/session_start_hook.py`）が、未完了の記録・main 以外のブランチ・未コミットの変更・直前のコミットを先に知らせる。

1. **未完了の作業を探す**: `.claude/progress/` の `_template.md` 以外のファイル、`git branch` の main 以外のローカルブランチ。
2. **記録と実際の状態を照合する**: `git status` / `git diff`、`git log --oneline <base>..HEAD`、エディタのアセット（MCP の `AssetTools.find_assets` や `list_folders`）、「再開時の注意」の出力。
3. **食い違いを直す**: git・実ファイル・アセットの状態を正として記録を直す。どちらが正しいか決められないときは、ユーザーに確認する（無人モードでは捨てずに残して要確認に書き、触らずに進められるステップへ）。
4. **途中のステップを扱う**: 変更を捨てる（`git checkout -- <file>`、`git restore`、`git reset --hard`、`git stash`、アセットの削除など）ときは、先にユーザーに確認する。記録にないファイルやアセットの変更はユーザーの作業かもしれないので触らない。
5. **ベースラインを確かめる**: エディタが起動して MCP が応答すること、C++ がビルドできること。
6. **再開する**: 「次にやること」から続け、再開したことと照合で見つけたことを記録に書く。
