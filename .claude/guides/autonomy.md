  - 不具合の改善

- **無人運転と有人セッションを同時に動かさない**。同じ作業ツリー・エディタ・git を取り合う。駆動役は、動いている間 `Intermediate/Overnight/driver.json` を置く。SessionStart hook は、このファイルで駆動役が動いているかを見て、有人セッションに知らせる。

## 無人モード

- **合図**: 環境変数 `WASAMI_UNATTENDED=1`。駆動役 `Tools/overnight.py` が `claude -p "/continue"` を起動するときに付け、SessionStart hook（`.claude/scripts/session_start_hook.py`）が「無人モード」を文脈に入れる。この合図が無ければ有人セッションで、人がいるときの決まりどおり（質問してよい、`/clear` を頼む）。することは下の「有人セッション」。
- **誰が回すか**: Claude は自分で `/clear` を実行できない。駆動役が `claude -p "/continue" --permission-mode auto` を繰り返し、**Claude がステップを終えて応答を終える（プロセスが終わる）ことが「文脈を消して続行」の合図**。反復にタイムアウトは無い（ユーザーの回答）。
- **起動**（ユーザーが、Claude Code の外の端末から。セッションの中からは入れ子になるので断る）: `python Tools/overnight.py --until 07:00 --usage-cmd "<使用量を JSON で出すコマンド>"`。
  - `--until` は止める時刻。省けば予算・`stop`・進捗なしまで回る。
  - 使用量を読まずに回すなら `--no-usage-check`。
  - `--dry-run` は計画と起動の確認だけ。`--max-iterations N` は反復の上限。
  - 別の駆動役が動いていれば起動を断る（`driver.json`）。
- **1 反復 = `/continue` の 1 ステップ**（`.claude/skills/continue/SKILL.md`）。記録と git とエディタの状態だけから再開し、ステップを 1 つ終えてコミットし、終える。
- **バックグラウンドの作業を残して応答を終えない**（2026-09-18。反復が調査のサブエージェント 3 本を「待っています」と書いて応答を終え、`claude -p` が 600 秒で打ち切って、調査もコミットも状態ファイルも失われた。症状索引の「`Background tasks still running after 600s`」）。無人モードでは、応答を終えることが反復の終わり（プロセスの終わり）になる。
  - サブエージェント（`Agent`）は前面（`run_in_background: false`）で呼ぶ。いくつも並べるなら、1 つのメッセージに前面の呼び出しを並べる。
  - `run_in_background` のコマンドや `Monitor` を使ったら、応答を終える前に終わりを待って結果を読む。
  - 「〜を待っています」で応答を終えない。
- **セッションの終え方**（`/clear` を頼む代わりに）:
  1. コミットまで終える（記録の更新を含む。`.claude/guides/progress-tracking.md`）。
  2. 状態ファイル `Intermediate/Overnight/status.json` を書く: `{"result": "continue" | "stop", "reason": "<理由>", "step": "<終えたステップ>", "commit": "<HEAD の短縮ハッシュ>", "written": "<ISO 8601>", "done": "<1 行>", "summary": [...], "learned": [...], "pending": [...], "shots": {"caption": "...", "files": [...]}}`。`continue` はまだやることがある、`stop` はこの運転はここまで（理由は必ず書く: 大目標 N（名前）を達成 / 進行中の大目標が無い / 要確認で進めない / 直せない失敗 / 予算）。後ろの 5 つは Discord の反復の報告と終わりのまとめになる（書き方は下の「Discord への通知」）。
  3. 最後の応答に「何が終わったか・次に何をするか・要確認の件数」を 1〜3 行書く（駆動役がログに残す。Discord には送らない）。
- **Discord への通知**（2026-09-17 のユーザーの指示「無人運転中の Claude の応答を、Discord webhook に投げてください」「名前は Claude に」「ステップ内で本作ゲームをスクリーンキャプチャした際、その画像も送る」。画像は 2026-09-18 の指示で、人に見せる連番のグリッドだけを反復の報告にまとめて付ける形に変わった）: 送り主の名前は「Claude」。送る処理は `Tools/discord_notify.py`。URL は環境変数 `WASAMI_DISCORD_WEBHOOK`、無ければ `Tools/overnight.local.json` の `discord_webhook`（git の外。URL を知っていれば誰でも投稿できるので、リポジトリ・記録・コミット・出力には書かない）。送れなくても止まらない（1 行知らせる）。
  - 駆動役が、開始・反復ごとの報告（下）・待機・終わりのまとめ（下）を送る（`--no-discord` で送らない）。
  - **反復の報告**（2026-09-18 のユーザーの指示「Discord WebHookのフォーマットは、次のサンプルを元に修正してください」）: 反復が終わるたびに 1 通。形は下のとおり。見出しはサンプルの `####` を `###` にした（Discord の見出しは `###` までで、`####` は文字のまま出る）。**節の見出し（サンプルの `####`）の直後に空行を入れない**（2026-09-18 のユーザーの指示「Discordフォーマットの見出し4の後の改行は不要です」。終わりのまとめと開始の投稿も同じ）。
    ```
    ## 📌 反復 #<n> 終了
    ### ステータス          … exit・作業時間・進捗率
    ### 🔧 作業概要
    ### 💡 分かったこと
    ### 🚨 要検討事項       … 無ければ「なし」
    ### 📷 スクショ         … 何の絵かの 1 文と、画像をグリッドで添付
    ```
    - exit と作業時間は駆動役が測る。**進捗率**は、全体の発足〜最終目標を母数にした概算で（ユーザーの指示）、駆動役が作業一覧の規模から計算する（`.claude/roadmap.md` の「進捗率」）。括弧の中に、進行中の大目標の進み（同じ計算をその節の項目だけで）を添える。
    - ほかは状態ファイルの欄から組む。Claude が書くもの:
      - `done`（終わりのまとめの「やったこと」）: この反復でしたことを 1 行（20〜40 字ほど。例:「星屑を本家の式から直接参照した」）。反復の報告には出ず、終わりのまとめに反復の順で並ぶ。
      - `summary`（作業概要）: この反復でしたことを 1〜3 項目。コードを読んでいない人に分かる言葉で、1 項目 1〜2 文。
      - `learned`（分かったこと）: この反復で新しく分かった事実（原作の作り、道具やエンジンの癖、試して駄目だった案）。無ければ `[]`。
      - `pending`（要検討事項）: **この反復で新しく要確認に書いたものだけ**を 1 件 1 文で。前の反復からある要確認は、書き足しても載せない（ユーザーの指示「その反復内で発生したものを書くようにし、前の反復を持ち越さない」）。無ければ `[]`。
      - `shots`（スクショ）: **人に見せるべき画像だけ**（2026-09-18 のユーザーの指示）。この反復で作った見た目や動きを、人が見て分かる形にしたもの: 特殊効果・敵の動き・シャードの回収などの連番のグリッド。`files` に画像（リポジトリの直下からの相対パスか絶対パス。**10 枚まで**。1 通に付く画像を Discord がグリッドに並べる）、`caption` に何の絵かの 1 文（例:「Primary Fear の検証連番画像をグリッドで添付します。」）。連番は PIE の収録を `python Tools/video_probe.py sheet <動画> <out.png>` で 1 枚のグリッドにする（コマごとの時刻が入る）。人に見せる画像が無い反復は `shots` を省く（「なし」になる）。
        - **付けないもの**（同じ指示）: 作業中に確かめるために撮ったもの、UE5 エディタの 1 つの調整の画面、デスクトップ全体の画面。
        - **本家の絵を含む画像は付けない**（本家の画面、本家と並べた比べる画像）。
    - 欄が無いときの代わり: `done` → `summary` の先頭の 1 項目。`summary` → Claude の最後の応答。`pending` → 反復の間に進捗記録の要確認に増えた行。`shots` → 付けない（駆動役は撮った画面を自動では付けない）。
    - **成果の無い反復**（状態ファイルが書かれず、HEAD も動かない。2026-09-18 から）: exit 0 でも、見出しを `## ⚠️ 反復 #<n> 終了（成果なし）` にし、ステータスに「結果」の 1 行を足す（出力に `Background tasks still running` があれば、その原因の 1 行も）。終わりのまとめの「やったこと」にも「反復 <n>: 成果なし」を入れる。
  - **終わりのまとめ**（2026-09-18 のユーザーの指示「無人運転終了時のDiscord通知は、次のフォーマットで。」）: 駆動役が止まるときに 1 通。形は下のとおりで、見出しは反復の報告と同じくサンプルの `####` を `###` にした。
    ```
    # 🏁 無人運転終了

    - 反復回数: 23回
    - 無人運転時間: 7時間14分
    - 終了理由: スケジュール時刻を迎えたため

    ### 🔧 やったこと     … 各反復の `done` を反復の順に
    ### 🚨 要確認事項     … 各反復の `pending`（その反復で新しく出たもの）を合わせたもの。無ければ「なし」
    ```
    - 反復回数・無人運転時間（駆動役の起動から終わりまで。待機を含む）・終了理由は駆動役が出す。終了理由は「〜ため」の 1 文（`--until` なら「スケジュール時刻を迎えたため」、ほかに反復の上限・予算・使用量が読めない・Claude の `stop`〈その理由を括弧で〉・コミットが増えない・起動できない・Ctrl+C）。詳しい理由・HEAD・進捗記録の要確認の全件はログのまとめにだけ書く。
  - **画像は反復の報告にまとめて付ける**。反復の途中で `desktop.py shot` を撮っても送られない。`discord_notify.py` で別に送ることもしない。
- **駆動役が止める条件**（Claude は気にしなくてよい）: 状態ファイルが `stop`、**進行中の大目標の項目がすべて完了になった（大目標の達成。Claude が `stop` を書き忘れても止まる。次の大目標の始め方が「自動」なら止まらず、Discord に「🎯 大目標 N を達成」を送って次の大目標へ続ける）**、反復の前後で HEAD が動かないことが 2 回続いた（進捗なし）、予算（下の「予算」）、`--max-iterations` / `--until`。**起動のときに進行中の大目標が無ければ、起動を断る**（終了コード 6。前の大目標を達成したまま次を進行中にしていない。次の大目標の始め方が「自動」なら断らない）。

## 何を作業するか

- **作業一覧** `.claude/roadmap.md`（1 項目 = 進捗記録 1 件。各項目に「目標 / 完了の条件（何を測って何に合えば終わりか）/ 根拠の置き場 / 依存 / 規模 / 状態」）。最終目標はユーザーが示し、Claude が段階（項目）に分解する。大規模な項目は、進捗記録の中でさらにステップに分ける（`.claude/guides/git-workflow.md` の大規模改修）。
- **大目標**（2026-09-18 から。`.claude/roadmap.md` の「大目標」）: 項目は `## 大目標 N:` の節に分かれ、各節の頭の `- 状態:` が 未着手 / 進行中 / 達成（日付）。**進行中は 1 つだけ**。
  - **取る項目は、進行中の大目標の節の中だけ**。ほかの節の項目は、依存が満たされていても始めない。
  - **大目標を「進行中」にするのはユーザーだけ**（有人セッションで指示を受けて書き換える）。無人運転は書き換えない。**例外は、節の頭の `- 始め方:` が「自動」の大目標**（いまは大目標 2。2026-09-19 のユーザーの指示）: 前の大目標を達成したら、無人運転が「進行中（日付から）」にする。
  - **進行中の大目標の最後の項目を閉じたら**（節の項目がすべて「完了」）、同じ反復で大目標の状態を「達成（日付）」にする。
    - 次の大目標の始め方が「自動」なら、同じコミットで次の大目標を「進行中（日付から）」にし（その大目標の項目の `status: 保留` の記録は `進行中` に戻す）、状態ファイルは `continue`（`done` に「大目標 N を達成し、大目標 N+1 へ移った」）。次の反復が、その節の「未着手」で依存が満たされた最初の項目から始める。handover の「遊んで確かめる手順」は書いておく（ユーザーが後で遊べるように）。
    - そうでなければ、状態ファイルに `stop`（理由「大目標 N（名前）を達成」）を書いて終える。次の大目標の計画は立てない。
  - **進行中の大目標が無い**（前の大目標を達成したまま）ときは、次の大目標の始め方が「自動」ならそれを「進行中（日付から）」にしてコミットし、最初の項目から始める。そうでなければ何も始めずに `stop`（理由「進行中の大目標が無い」）。
  - **決め方も大目標で変わる**: 大目標 1・2 は見た目を本家と見比べて詰めない（`.claude/roadmap.md` の「大目標 1・2 の決め方」。下の「決め方」の階段の 2 と「線引き」の見た目）。
- **進捗率のために**（Discord の報告。`.claude/roadmap.md` の「進捗率」）: 作業一覧の項目の進捗記録は、`# ` の題に「（作業一覧の項目 N）」を入れ、「計画」のステップを字下げの無い `- [ ]` / `- [x]` で書く。項目を足すときは規模も書く。
- **進捗記録が無いとき**は、進行中の大目標の節の「未着手」で依存が満たされた最初の項目を取り、**最初の反復は計画だけ**（進捗記録を作り、ステップに分け、コミットして終える）。計画は有人セッションでユーザーが見直せる。作業一覧が無いか空なら、handover の「次の一歩」から取る。
- **進捗記録が複数あるとき**は、`status: ユーザー待ち` と `status: 保留`（進行中でない大目標の項目の記録）を飛ばし、残りをファイル名の順（古い順）に扱う。残りが無く、全部がユーザー待ちなら `stop`。保留だけなら、記録が無いときと同じ。
- 項目が終わったら、作業一覧の状態を「完了（日付）」にし、次の項目へ（同じ反復では始めない。計画は次の反復で）。

## 決め方（人に聞けないとき）

- **質問しない**。`AskUserQuestion` は使わない（`-p` では答えが来ない）。「〜してよいですか」も書かない。
- **決め方の階段**。上から順に試し、決まったところで進む:
  1. 本家のコード（`pak_reference_2/`。テレポーテーションは `pak_reference/`。`.claude/guides/original-fidelity.md`）。両版にあって違うものは、**最新版を仮に採って**要確認に書く。最新版に無いので旧版から写す画面があっても、旧版に合わせるのはその画面だけで、両版にあるほかの画面・仕組みの規則は最新版を採る（2026-09-19 の回答: オプション画面を旧版から写しても、死亡画面の EASY の分岐は最新版）。
  2. 手元の本家の実機の観察（無人運転でも行ってよい。エディタを閉じてから起動し、終わったら閉じて開き直す。`.claude/guides/verification.md`）。**大目標 1・2 では、ゲームの規則がコードで決まらないときだけ**使い、見た目のためには起動しない（飛ばして 3・4 へ）。
  3. WebGL 版の仕様と記録（`.claude/references/webgl/`）。
  4. **仮の値**で進める。候補のうち、原作に最も近く・最も小さく・後で戻しやすいものを選ぶ。
- **線引き**（ユーザーの回答）:
  - **仮で進めてよい**: 見た目（推定の材質・粒子・色・大きさ・速さの見え方）、演出のタイミングの細部、本作独自の部分の作り。**大目標 1・2 では見た目の仮の値は要確認に書かず**、作業一覧の項目 28 の「後回しの一覧」に 1 行書く（大目標 3 でまとめて詰める）。
  - **仮で進めない**: ゲームの規則の値（速さ・秒数・個数・回数・条件・順序）が本家のコードに無い・読めないとき。そのステップを記録で「ユーザー待ち」にし、依存しない次のステップへ。無ければ `stop`。
  - **音の確認と主観の見比べ**は無人運転ではできない（人が聞く・見る）。本作の側の収録や画面を `observations/` に残し、要確認に書いて進む。
- **仮の値の残し方**: コードには `// TODO(仮): 何を仮にしたか・なぜ・要確認の項目名` を付け、記録の「要確認（ユーザー）」に 1 行書く（下）。実装記録には「推定」と明記する（原作への忠実さのガイドと同じ）。
- **記録と実際の食い違い**で正しい方を決められないときは、**捨てずにそのまま残し**、要確認に書いて、触らずに進められるステップへ。進めないなら `stop`。
- **計画を大きく変えたくなったとき**（人がいればユーザーに確認する場面）は、変更案を要確認に書き、**変えずに進められる範囲で進む**。変えないと進めないなら `stop`。

## 要確認（ユーザー）

- 進捗記録の `## 要確認（ユーザー）` の節に、有人セッションでユーザーがまとめて答えられる形で 1 件 1 行: `- <日付>: <何を> — 仮に <何にした>。理由: <根拠>。場所: <ファイル・関数・TODO(仮) の文言>`。
- 答えが出たら、その場で「決定事項」に移し、仮の値を直して `TODO(仮)` を外す。
- SessionStart hook が、未完了の記録の要確認と前回の状態ファイルを起動時に出す（有人セッションの始めの一覧）。

## 止まるもの・飛ばすもの

- **無人運転では行わない**（人がいるときは確認してから行うもの）: 変更を捨てる操作（`git checkout --`・`restore`・`reset --hard`・`stash`、記録に無いアセットやファイルの削除）、配布とパッケージ、本家のセーブの中身を手で書き換えること（遊んで書き換わる・控えから戻す・入れ替えるのは無人運転でもしてよい。`verification.md`）、force push、第三者のコードの組み込み、Steam の登録の変更。必要になったら要確認に書き、その作業は飛ばす。
- **同じ失敗（同じエラー、同じ落ちるテスト）への修正の試みは 2 回まで**。3 回目には症状索引（下）に「未解決」で書き、そのステップを飛ばすか、飛ばせなければ `stop`。
- **エディタが落ちた・起動しない**: `python Tools/editor_cycle.py` を 1 回やり直す。それでも駄目なら理由を書いて `stop`。
- **ビルドが通らない変更はコミットしない**。直せなければ変更はそのまま残し（捨てない）、記録の「再開時の注意」と要確認に書いて `stop`。
- **PIE と本家のゲーム**は、反復を終える前に必ず止める（次の反復が照合で困る）。

## git（無人運転の範囲）

- 実装ごとにコミット、作業ブランチ → main へのマージ、ローカルブランチの削除、main の push はすべて無人運転でも行ってよい（ユーザーの回答。`.claude/guides/git-workflow.md` の条件どおり）。
- push が拒否されたら force push せず、要確認に書いて続ける（push は進行を止めない）。

## 予算と環境

- **週間の枠**（`/usage` の 7 日）: リセットまで 3 日以上あるのに残りが 50% を切る、または 1 日以上あるのに 25% を切ったら止める（ユーザーの回答）。**5 時間の枠**が尽きたらリセットまで待って続ける。使用量が読めなければ止めて報告する。判定は駆動役が反復の前に行う。**駆動役は使用量を自分では読まない**（OAuth の認証情報や CLI の内部に触れない。2026-09-17）。`--usage-cmd "<コマンド>"` で読み方を差し込む（そのコマンドは `{"seven_day": {"utilization": 0〜100, "resets_at": "<ISO 8601>"}, "five_hour": {…}}` を標準出力に出す。`five_hour` は省略可）。差し込みが無ければ「使用量が読めない」で止まる。`--no-usage-check` を付けたときだけ読まずに回し、Claude の返事の「usage limit reached」を 5 時間の枠の合図にして、返事にあるリセットの時刻（無ければ 30 分）まで待つ。
- 権限モードは `auto`（`bypassPermissions` は使わない）。
- 画面: ユーザーは Chrome Remote Desktop で操作し、HDMI にダミーモニタを付けてある（ロック・スリープの対策済み。2026-09-17）。対話デスクトップ（セッション 1）の操作エージェント（`Tools/desktop.py`）は 30 分無入力で終わるので、反復ごとに `start` する。
- Docker Desktop は止めてある（MCP の 127.0.0.1:8000 と衝突していた）。反復の始まりにエディタが起きていれば MCP はつながる。反復の途中でエディタを開き直した後は `Tools/ue_remote.py` で続ける（`/mcp` は打てない）。

## 症状索引

- `.claude/references/troubleshooting.md`。**引く**: エラー文やおかしな挙動に会ったら、まずこのファイルを grep する。**書く**: 解決にエディタの開き直し 1 回以上、または 30 分以上かかったら、次に進む前にその場で書く（「2 回目に会ったら」では遅い）。直さなくてよい既知の見え方と、試して駄目だった案も書く。

## 有人セッション（2026-09-18 から）

無人モードの合図（`WASAMI_UNATTENDED=1`）が無いセッション。作業一覧を進める場ではなく、無人運転の結果を直す場。

### 始め方

- SessionStart hook が次のものを出す。
  - 前回の無人運転の状態ファイル
  - 最新の駆動役のログのまとめ
  - 未完了の記録と、その要確認
- これをもとに、次の 3 つを短く報告して、ユーザーの指示を待つ。
  - 無人運転で何が進んだか（ログのまとめと、その間のコミット）
  - 大目標の状態（hook が出す。達成で止まっていたら、ユーザーが遊んで確かめる手順〈handover の「現状と次の一歩」〉も添える）
  - 要確認の一覧
- 自分から `/continue` で作業一覧を進めない。

### 駆動役が動いているとき

- hook が「駆動役が動いています」と知らせたら、ファイル・エディタ・git を変える前に、ユーザーに駆動役を止めてもらう（端末で Ctrl+C）。
- 読むだけの調べものと報告は続けてよい。
- 止めたのが反復の途中なら、直す前に `/continue` の「照合」（記録・git・エディタの食い違い）だけを行う。

### 方向性・実装方針の修正

- ユーザーの指摘は、**無人運転が次に読む場所へその場で書く**。会話にしか無い決定は、次の無人運転に伝わらない。

| 指摘の種類 | 書く場所 |
| --- | --- |
| いまの作業のやり方 | その進捗記録の「決定事項」。計画が変わるなら「計画」と「次にやること」も |
| 作業の順・目標・完了の条件 | `.claude/roadmap.md` |
| 次の大目標を始める（ユーザーの指示があったときだけ。始め方が「自動」の大目標は無人運転が始める） | `.claude/roadmap.md` のその大目標の節の `- 状態:` を「進行中（日付から）」に。大目標 3 は、先に項目 28 の後回しの一覧をユーザーと見直して項目を立て直す。その大目標の項目の `status: 保留` の記録は `進行中` に戻す |
| これからずっと効く決まり | 該当するガイドと、`CLAUDE.md` の索引の 1 行 |
| 要確認の答え | 「決定事項」へ 1 行で移し、仮の値を直して `TODO(仮)` を外す。`status: ユーザー待ち` の記録は `進行中` に戻す |

- 直すこと（コードやアセットの変更）は、大きさで分ける。
  - 小さいもの・ユーザーがその場で確かめたいもの → 有人セッションで直す。
  - 数ステップにわたるもの → 記録の計画にステップとして足し、無人運転に任せる。
- 指摘が無人運転の決め方の穴から来ていたら、その決まりもこのガイドに足す。例: 仮の値の選び方、確かめ方の不足。次の無人運転で同じことを繰り返さないため。

### 不具合の改善

- ユーザーが報告した不具合を、有人セッションで直す。
- いつもどおり、進捗記録を先に書く。小さければ「依頼」「計画」「次にやること」だけでよい。
- どのブランチで直すか:
  - いまの作業ブランチの作業に関わる不具合 → そのブランチで直す。
  - 関わらない不具合 → main で直す。そのあと作業ブランチへ main をマージして、無人運転がその直しの上で続くようにする。
- 症状索引（`.claude/references/troubleshooting.md`）に書く条件はいつもどおり。
- 直しが 1 つ終わったら、記録を残して `/clear` をお願いする（`.claude/guides/progress-tracking.md`）。

### 終え方（無人運転に戻す前）

1. 変更をすべてコミットする。未コミットの変更が残っていると、無人運転はそれをユーザーの作業とみなして触らない。
2. 修正が記録・作業一覧・ガイドに入っていることを確かめる。
3. PIE と本家を止める。エディタは保存して、開いたままにする。
4. 無人運転に戻せることを、駆動役の起動のコマンドと一緒に 1 行で伝える。

## 結果の見方（ユーザー向け）

1. 新しいセッション（有人セッション）を開くと、SessionStart hook が上の「始め方」のものを出し、Claude がそれをもとに報告する。大目標を達成して止まったときは、遊んで確かめてから「次の大目標へ」と伝える（それまで駆動役は起動を断る）。始め方が「自動」の大目標（いまは大目標 2）へは止まらずに移るので、前の大目標は Discord の「🎯 大目標 N を達成」と handover の手順で後から遊んで確かめる。
2. 無人運転の間の様子は Discord で見られる（開始・反復ごとの報告〈ステータス・作業概要・分かったこと・要検討事項・人に見せる連番のグリッド〉・待機・終わりのまとめ〈反復回数・無人運転時間・終了理由・やったこと・要確認事項〉）。
3. 生の足跡は `Intermediate/Overnight/<YYYYMMDD-HHMM>.log`。駆動役の起動ごとに 1 つで、反復ごとの Claude の最後の応答・HEAD・使用量と、末尾のまとめが入る。
4. 要確認に答えると、Claude がその場で決定事項に移して仮の値を直す。
