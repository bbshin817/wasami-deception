# 原作への忠実さの運用ルール

WebGL 版の同名のルール（`<WEBGL>/.claude/guides/original-fidelity.md`、`<WEBGL>` = `C:\Users\User\Downloads\wasami-deseption`）を UE5 版に移したもの。実装は基本的に本家（原作『Dark Deception』）に忠実に倣う。値・時間軸・音・演出・挙動は、まず原作データから確かめ、原作データで確定できない部分は本家を入念に観察してから決める。

## 本作の規範（2026-09-15、ユーザーの指示）

1. スピードブースト・テレポーテーション・タブレットの挙動・モーションブラーなど、あらゆる要素は本家（`pak_reference/`）に基づく。

3. 本家にないギミックを足すときは、複雑にしない。壊せる物は、本家のホテルの板張りのバリケード（`BP_01_Woodboards`）のように 1 回のクリックで崩れ、自然に消える。初めて遊ぶ人でも、特別な案内なしに遊べることを保証する。

- 本家どおりの挙動がわかりにくく見えても、規範 1 に従って本家どおりにする。

## UE5 版で足したこと（2026-09-16）

- 本家（UE 4.21 / 4.24）もステージの原作（UE 5.4）も UE で作られている。**UE に同じ仕組みがあるものは、原作データの値をその仕組みに写すだけにし、作り直さない**（CharacterMovement の速さと加減速、ポストプロセスの設定、灯の単位と減衰、SoundCue の減衰、カメラシェイク、UMG のアンカーとアニメなど）。WebGL 版がブラウザで UE を再現するために作った近似（トーンマップの LUT、ライトマップの焼き直し、衝突の格子など）は持ち越さない。
- WebGL 版で決めたこと（ユーザーの回答、推定した値とその根拠）は、UE で原作データの値をそのまま使える場合を除いて引き継ぐ。WebGL 版の制約から来た決定（例: ブラウザで終了できないので QUIT TO DESKTOP を置かない）は、UE5 版では本家どおりに戻してよいか、ユーザーに確認する。
- エンジンの版の違い（UE 4.21 と 5.8）で既定値や挙動が変わるもの（トーンマップ、露出、モーションブラー、ブルームなど）は、原作の見え方に合わせる方を採り、違いと判断を記録に書く。

## 原作データの調べ方

- 最初に `pak_reference/README.md` と `_manifest.json` で、どこに何があるかを確かめる（Blueprint のバイトコード `_bytecode/`、全アセットのプロパティ `_assets/`、カメラ `_camera/`、SoundCue `_soundcues.json`、マテリアル `_materials.json`、パーティクル `_particles.json`、レベル配置 `_levels/`、音 `.ogg`、テクスチャ `.png` など）。
- 大きい JSON は全体を会話に読み込まず、スクリプトで必要な部分だけ抜き出す。
- Blueprint の処理はバイトコードの実行経路（イベント入口 → 分岐 → 呼び出し）をたどり、呼び出しのリテラル引数まで確かめる。再生時の値は、呼び出し側の引数と参照先アセット自身の設定の両方で決まることがあるので、両方を見る。
- 本家の座標は UE の cm・Z 上のまま使える（WebGL 版のような座標変換は要らない）。`_levels/*.scene.json` の `world` はアタッチ階層を合成済みの絶対変換。
- `pak_reference_2` のメッシュは CUE4Parse の glTF（`_meshes_gltf/**.gltf` + `.bin`、LOD0 のみ、UV 8 組、頂点色つき、マテリアル名はスロット名）。`pak_reference` の umodel 版とは書き出し器が違う。
- WebGL 版の記録（`<WEBGL>/.claude/implementation-records/`）には、原作データのどこから値を取ったか（アセット名・関数名・バイトコードのオフセット `@1234`）が書いてある。同じ要素を作るときは、まずそこを引く。

## 原作データで確定できないとき

cook で消えた情報（ベースマテリアルの式の多く、ベイク済みライティング、動画、エディタ上の設定）や、実行時にしか決まらない見え方・手触りは、原作データだけでは確定できない。推測で埋めずに次の順で進める。

1. **切り分ける**: 原作データから確定できる範囲を先に確かめ、確定できない部分を具体的に絞り込む。
2. **観察する**: 手元の参考映像や、これまでに受け取った収録で観察する。足りなければ、上の「本家のゲームを手元で動かす」に従って**実機で観察する**（その場面がこのビルドで出せるかを先に確かめる）。
3. **収録を求める**: 観察に足る映像がなく、実機でも出せない場面（病院、新しい版の効果）のときは、ユーザーに本家の画面収録を依頼する（確かめたいこと、再現の手順、撮り方〈60fps・解像度・音声・UI の有無〉を書く）。
4. **測る**: 収録をコマ単位で見て、時間・大きさ・色・動きを測る。本作の同じ場面を同じ条件で撮り、並べて比べる。
5. **検討して決める**: 候補が複数あって見た目や手触りを大きく左右するときは、候補と根拠を示してユーザーに確認する。
6. **記録する**: 観察から決めた値は「推定」と明記し、何から・どう推定したかを書く。
